# ZCode auto-memory as a two-way mirror of the ledger

Date: 2026-08-30. Status: accepted.

## Context

The ledger's schema (one file per durable fact, frontmatter `name`/`description`/`type`, `MEMORY.md` index) was modeled on ZCode's auto-memory (`~/.zcode/cli/memories/projects/<project>-<hash>/memory/`). The two stores are schema-isomorphic, so the owner wants them linked both ways: ZCode sessions keep their native memory experience, while the repo ledger stays the canonical, cross-host store.

## Decision

- **Canonical**: the repo ledger (`.memory/`) remains the only source of truth. The ZCode memory dir for the same project is a **mirror**, regenerated by `node dist/cli.js sync` — never hand-curated as a second master.
- **Sync is deterministic**: three-way reconcile against `.memory/.sync-zcode.json` (per-side content hashes from the last pass). Edit beats unchanged; a true both-sides edit resolves by mtime (reported as `conflict-resolved`); a deletion propagates only when the other side did not edit since the last sync. No LLM, no background process — sync runs explicitly at a session boundary.
- **Pin is push-only**: pinned ledger topics reach ZCode, but a ZCode-side edit never overwrites the pinned original; the tampered mirror copy is repaired from the ledger and reported as `skip-pinned`.
- **Format conversion**: ledger → ZCode strips ledger-only frontmatter (`node_type`, `origin`, `pin`, legacy `conflict`); ZCode → ledger preserves the ledger's `origin`/`pin` and imports `name`/`description`/`type`/`body` as-is. Matching is by frontmatter `name`, not filename.
- **Index upkeep**: sync maintains ZCode's `MEMORY.md` lines for topics it pushed or deleted; pre-existing ZCode index rows are ZCode's agent's business and are not rewritten.
- **Discovery anchor**: sync writes a `project-memory-ledger.md` pointer memory (type `reference`) into the ZCode project memory dir naming the ledger path. It is excluded from mirroring and doubles as the in-session hint to ZCode agents that the ledger exists.
- **Grok stays one-way** (export only): Grok's native memory is freeform headings plus an LLM auto-dream that rewrites content, so round-tripping would sync dream's rewrites, not the ledger.

## Consequences

- ZCode sessions see ledger topics natively (their `MEMORY.md` gains the mirrored rows) without project-memory hooks — the ZCode hook wiring stays disabled.
- Content diverging in the mirror is always reproducible from the ledger; the snapshot makes deletion detection safe.
- The ZCode memory format is observed, not contracted: if ZCode changes its schema, sync reports unreadable files and skips them rather than guessing.
